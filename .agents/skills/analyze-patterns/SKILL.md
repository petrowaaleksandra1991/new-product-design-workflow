# Analyze UX patterns

## Inputs and role

Apply the [pattern analyst profile](../../roles/pattern-analyst.md).

First check `PROJECT-STATUS.md` and the research solution. Take from the accepted `RESEARCH.md` “The Main Thing in a Minute” and questions that require a UX answer; from `RESEARCH-REVIEW.md` - trust restrictions if review is completed. If you skip an entry, show the risk recorded and do not portray it as approved evidence. Open detailed evidence chains and applicable sections of `PRODUCT-CONTEXT.md` only for the task being compared. Don't use outdated or rejected output as a basis.

Create `PATTERN-ANALYSIS.md`. For each user task, find several real models through available screen catalogs, official recommendations, products, public cases and web sources.

Describe the pattern, not just the screenshot: context, decision structure, states, errors, recovery, accessibility, benefits, risks, data/technical implications and source. Assess fit to evidence, outcomes and limitations.

Show that you can `reuse`, `adapt`, `combine`, `avoid` or check. In conveying the result, briefly highlight the selected models, their sources, reasons for suitability, rejected alternatives and questions for PRD. If the user selects a specific solution, record the source, aspect chosen, and adaptation. Don't copy someone else's brand and go with the UI. Pass it to `in-review` and stop for the user to decide.
