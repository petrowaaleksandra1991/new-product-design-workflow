# Define visual direction

## Inputs

Read `PROJECT-STATUS.md`, the approved `VISUAL-REFERENCE-ANALYSIS.md`, the applicable UX decisions and user selections, and only the relevant durable entries in `PRODUCT-CONTEXT.md`. If reference analysis was skipped, record the substitute input and accepted risk.

Collect 1-3 text directions only with a real choice. For each, show the character, hierarchy, layout logic, typography, color role, shape, imagery/iconography, density, motion and UX impact. Don't draw several expensive concepts before choosing if the text is enough.

When formulating rules, use the section “Visual direction” [interface techniques](../../../product-design/sources/INTERFACE-CRAFT-METHOD.md): define roles and boundaries of application, and not universal numerical recipes.

After the user's decision, create `VISUAL-DIRECTION.md`: approved rules, required assets, permissible deviations, preliminary values and counterexamples. Mark everything as `direction`, not production tokens. Stop in front of high-fi.

When the user approves this version, update only the `Current visual direction` index in `EMERGING-SYSTEM-STATUS.md` with a reference to the solution and version. Do not mark provisional values as `implemented` or `verified`.
