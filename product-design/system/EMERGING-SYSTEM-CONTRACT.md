# Contract for an evolving design system

In the new product, visual rules appear gradually. The contract separates the search for a solution from the formalization of the system.

| Status | Meaning | Resolution |
|---|---|---|
| `exploratory` | Local Research Screen Solution | change in working scope |
| `candidate` | repeatability noticed and described | compare uses and conditions |
| `approved-for-system` | user selected element | formalize contract and foundations |
| `implemented` | component or foundation created | use within version |
| `verified` | Versions, Accessibility and Reuse Tested | be considered an internal standard |
| `deprecated` | the solution is deduced | do not use in new works |

Codex may suggest `candidate`, but only the user's decision gives `approved-for-system`. Plan approval does not authorize publication. Foundations are created when they reduce variance or are needed by selected components.

The candidate is assessed on repeatability, state, variability, content, accessibility, responsive behavior, cost of support and likelihood of reuse. Visual similarity is not enough.
